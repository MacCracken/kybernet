## Independent verification

Ten of the findings below — including both CRITICALs — were **re-verified by hand during
the audit session**, not accepted on the sweep's report. Where that happened it is stated
under the finding. The two CRITICALs were each reproduced by execution: CRITICAL-1 under
`qemu-aarch64 -strace` against a probe compiled from kybernet's own source, CRITICAL-2 by
running the dereference and observing SIGSEGV.

⚠ **A caveat on the other 21, stated plainly.** The verification pass was configured to let
a finding survive if fewer than two of its two skeptics refuted it — i.e. a single
refutation did not kill it. That is a weaker bar than the 1.4.2 audit's, which refuted 13
of 39 candidates; this one refuted none, and that number should be read as a property of
the threshold rather than as evidence that every candidate was airtight. The findings that
were re-verified by hand are marked. **The unmarked ones carry the sweep's evidence, which
is detailed and specific, but they have not been independently reproduced — treat the
evidence, not the severity label, as the thing to check before acting.**

## Themes

Three themes dominate, and none of them is code that looks wrong on the page.

**1. aarch64 is a shipped release artifact that no gate has ever executed a single instruction of — and it does not boot.** `release.yml` builds `kybernet-<tag>-aarch64-linux`, checks its `e_machine`, and publishes it; `qemu/boot-test.sh` is x86_64/KVM only, and `cyrius test` runs native. So the arch half of the product ships on the strength of the cross-compiler exiting 0 (HIGH-9). What that blindness hid is CRITICAL-1: the cyrius aarch64 syscall table defines `SYS_FSYNC = 74` and `SYS_SIGNALFD4 = 74`, one deliberately borrowing the x86 number and one aarch64-native, and the backend's compatibility ladder — emitted inline into the binary, verified by disassembly — rewrites both to `fsync`. `sys_signalfd(-1, ...)` therefore issues `fsync(-1)`, phase 4 takes its FATAL arm, and every aarch64 board powers itself off before config load. The same ladder eats `SYS_PPOLL`, so `sys_pause()` returns `EINVAL` and every deliberate PID-1 halt becomes a 100% CPU spin with four rule-4 backstops silently disarmed (MEDIUM-9). This is standing rule 1's hazard reached from *inside* rule 1's own remedy: kybernet did route the call through a stdlib `sys_*` wrapper, and the wrapper is what is wrong. The unit suite cross-builds and runs under `qemu-aarch64` in two seconds — with three assertions that hardcode x86_64 constants, including the `epoll_event` data offset that was 1.4.2's CRITICAL-2, written so it can only ever pass on the arch where that bug never existed.

**2. The per-service confinement path applies materially less than it reports, and every shortfall answers `Ok`.** Six independent findings, all measured against a live kernel rather than read: Landlock rulesets are frozen at ABI v1, so `truncate(2)` is entirely unchecked for every confined service — a root service under a Landlock policy can zero `/boot/vmlinuz` while `sandbox_from_config` returns "applied" (HIGH-2). `capabilities` and `uid` cannot be combined at all, because the capability drop surrenders `CAP_SETUID`/`CAP_SETGID` two steps before the privilege drop needs them, and the obvious workaround starts the service with *zero* capabilities delivered (HIGH-3). A `landlock` block whose rules all grant nothing installs no ruleset and reports success (MEDIUM-1). `uid` without `gid` leaves the service at GID 0 (MEDIUM-6). A quoted `"uid"` or a non-string `"seccomp"` value silently discards the whole policy — while the sibling `limits` block, in the same file, refuses the service for exactly that mistake (MEDIUM-5). And a config service named after an argonaut built-in is counted in `services parsed: N` and then dropped whole, security block included, with no log line (MEDIUM-2). The 1.4.2 audit found this stack wired to nothing; it is now wired up, and the defects are in what it does once it runs.

**3. Timers, budgets and cadences derived from the wrong input set — and gates that cannot see the difference.** The health tick is computed from `config_services()` while the watchdog it must satisfy iterates the full registry, so on the default configuration PID 1 SIGKILLs a perfectly healthy compositor roughly twenty seconds into every boot and keeps doing it until the restart limit puts it down for good (HIGH-1). dm-verity inherits a hardcoded 10 s bound from an unset key that eleven lines of adjacent comment document as meaning *unbounded*, and reports the resulting SIGKILL as "veritysetup missing" while powering the board off (HIGH-8). Phase 7 re-decides the dm-verity verdict phase 6c deliberately declined to refuse on, reproduced on a live QEMU boot, defeating the one documented recovery path for a board locked out by a stale root hash (HIGH-7). `health_check` integers feed a kill decision with no bounds at all, fifty lines below a sibling field that is refused-not-clamped under a comment citing rule 25 (MEDIUM-3). Two exec paths still have no bound whatsoever (HIGH-6, MEDIUM-8). Underneath, three per-event allocations grow the one arena PID 1 never resets — one of them a 16x reintroduction, on the same datagram path, of a leak this repo shipped a fix for two releases ago and documented as closed (HIGH-4, HIGH-5, MEDIUM-10). Four of the findings are in the gates themselves: a `pipefail` abort that silently skips all five passes and deletes the logs whenever kybernet fails to boot, a one-character typo that makes `HARNESS_STRICT` inert, fixture inputs exempt from the staleness check rule 43 added, and the watchdog kill path running on every gate run with nothing asserting it. Standing rule 32's shape, four more times: a gate that runs the code and cannot report on it.

## CRITICAL-1 — aarch64: `sys_signalfd` issues `fsync(-1)`, so phase 4 fails EBADF and every aarch64 board powers itself off during boot

**Severity:** CRITICAL  **Where the fix lands:** `cyrius`  **Site:** `src/lib/signals.cyr:35`  
**Class:** arch-dependent syscall number hijacked by the cyrius aarch64 ESYSXLAT ladder — standing rule 1's hazard reached from INSIDE rule 1's own remedy

**Status:** **MITIGATED in 1.6.13; the fix is upstream.** cyrius is off-limits to this repo (CLAUDE.md), so kybernet closed the two things that ARE its own: (a) `scripts/aarch64-exec-gate.sh` executes aarch64 code in CI and carries this as a DECLARED known-broken entry that fails on drift in either direction; (b) `release.yml` now REFUSES to publish an aarch64 artifact that fails the boot-critical probe, rather than shipping a binary whose only outcome is poweroff. Filed for a cyrius fix; see roadmap.md.

> **Re-verified by hand.** Independently reproduced during this session, not taken on report: a probe compiled from kybernet's own `src/lib/signals.cyr` under `qemu-aarch64 -strace` shows `fsync(-1) = -1 errno=9`, and a 34-wrapper sweep of every `sys_*` kybernet calls shows **exactly two** wrong — `sys_signalfd -> fsync` and `sys_pause -> flock` — with the other 32 correct (including the ones that legitimately rename, `rmdir->unlinkat`, `epoll_wait->epoll_pwait`, `open->openat`). The x86_64 control is clean on all 34.

### Evidence

src/lib/signals.cyr:35 `var sfd = sys_signalfd(0 - 1, set, SFD_NONBLOCK | SFD_CLOEXEC); if (sfd < 0) { return Err(0 - sfd); }`. The stdlib wrapper is `syscall(SYS_SIGNALFD4, fd, mask, 8, flags)` (syscalls_linux_common.cyr:393), and the aarch64 peer defines TWO constants with the SAME value: `SYS_FSYNC = 74` (line 54, whose own comment says it DELIBERATELY emits the x86 number and relies on the backend ladder rewriting 74 -> 82) and `SYS_SIGNALFD4 = 74` (line 184, the aarch64-NATIVE number, which that ladder now eats). Verified in this repo's own lib/ copy: `grep -n '= 74;' lib/syscalls_aarch64_linux.cyr` returns both.

Proven by execution and by disassembly of the SHIPPED binary, not by reading. `aarch64-linux-gnu-objdump -d build/kybernet-aarch64` shows the translation emitted inline at every syscall site as a runtime compare-and-branch: `cmp x8, #0x4a (74) / b.ne / mov x8, #0x52 (82 = aarch64 fsync)`, with no later arm matching 82 — so x8=82 reaches `svc #0` on real silicon, not only under emulation. `qemu-aarch64 -strace` on a probe compiled from kybernet's own unmodified src/lib/signals.cyr: `rt_sigprocmask(SIG_BLOCK,[SIGHUP SIGINT SIGTERM SIGCHLD SIGPWR],NULL,8) = 0` then `fsync(-1) = -1 errno=9 (Bad file descriptor)`. Same source built for both arches: x86_64 -> Ok, fd 3; aarch64 -> Err(9). Tracing the real cross-built `build/kybernet-aarch64` shows the full sequence: the two phase-4 FATAL log writes, `sync`, then `reboot(0xfee1dead, 0x28121969, 0x4321fedc) = LINUX_REBOOT_CMD_POWER_OFF`.

Escape hatches checked empirically and REFUTED: `syscall(289,...)` (x86 signalfd4) and `syscall(1074,...)` both report "Unknown syscall" on aarch64, so there is currently NO way to reach signalfd4 from cyrius source on that arch.

### Trigger

Boot the published `kybernet-<tag>-aarch64-linux` artifact as PID 1 on any aarch64 board. No config, no service, no operator action; unconditional on every boot.

### Consequence

src/main.cyr:1518-1526 takes the FATAL arm on every aarch64 boot: `kmsg("phase 4: FATAL signal setup failed")` then `do_shutdown(SHUTDOWN_POWEROFF); sys_pause(); return 1;`. The board mounts filesystems, sets up the console, enables cgroup controllers, and then powers itself off at phase 4 — before config load, before argonaut, before any service, before the reactor. kybernet is 100% non-functional on aarch64. `sys_reboot` was separately verified to translate correctly, so the poweroff does land; if it did not, MEDIUM-9 turns this into `return 1` from `kybernet_run` = `sys_exit(1)` = "Attempted to kill init". release.yml builds, checks `e_machine`, and PUBLISHES this binary, and no gate has ever executed a single aarch64 instruction of it (see HIGH-9). Note the `sigprocmask` on the line above SUCCEEDS, so had the FATAL arm not existed the same defect would have produced a board with all signals blocked and no signalfd — never reaping, never shutting down.

### Fix

The load-bearing half is upstream in cyrius (which CLAUDE.md places off-limits to this repo, so it must be FILED, not patched here): give `SYS_SIGNALFD4` a private alias in the >=1000 band with an ESYSXLAT arm placed LAST in the chain — `SYS_SIGNALFD4 = 1074` with `1074 -> 74` — exactly the treatment `SYS_CHDIR = 1049` and `SYS_FCHOWNAT = 1054` already carry for this collision class (both were confirmed present in the emitted ladder). Kybernet-side, until a fixed toolchain is pinned: (a) make the aarch64 release step FAIL rather than publish a binary whose only outcome is poweroff, and (b) land HIGH-9's gate so this class cannot ship again. Do NOT "fix" it by weakening main.cyr:1519 — the error detection is correct; the primitive is not. Sweep every stdlib syscall kybernet reaches on aarch64 rather than point-fixing signalfd: the same ladder also hijacks `SYS_PPOLL = 73` (MEDIUM-9) and `SYS_UMOUNT2 = 39`.

## CRITICAL-2 — `_eb_compare_pcrs` reads sigil's raw cstr PCR digest as a boxed `Str` — wild-pointer dereference in PID 1 at phase 6c on the NORMAL success path of an attesting edge board

**Severity:** CRITICAL  **Where the fix lands:** `kybernet`  **Site:** `src/lib/edge_boot.cyr:316`  
**Class:** Str-vs-cstr type confusion / wild pointer dereference (standing rule 3)

**Status:** **CLOSED in 1.6.13.** `tpm_pcr_value_value()` is wrapped with `str_from()`, and baselines are now matched on `tpm_pcr_value_index` instead of positionally. `test_edge_compare_pcrs_cstr` builds the digest exactly the way sigil's producer builds it (`alloc`+`memcpy`+NUL) — verified to kill the whole test binary with SIGSEGV (exit 139) on the unfixed source.

> **Re-verified by hand.** Independently reproduced during this session: a probe building the digest exactly as `lib/sigil-tpm.cyr:676-679` does, then calling `str_len`/`str_data`/`load8` on it, exits **139 (SIGSEGV)**. `str_len(s)` is `load64(s+8)` and `str_data(s)` is `load64(s)`, confirmed in `~/.cyrius/lib/str.cyr:56,71`. The string is present in both DCE'd production binaries.

### Evidence

src/lib/edge_boot.cyr:314-321: `var got = tpm_pcr_value_value(vec_get(values, i)); var want = vec_get(_eb_expected_pcrs, i); if (edge_is_all_zero_hex(got) == 1) {...} elif (str_eq(got, want) == 0) {...}`. `got` is NOT a Str. sigil's producer builds it as a RAW cstr — lib/sigil-tpm.cyr:676-679 `hex_value = alloc(hlen + 1); memcpy(hex_value, outbuf + hstart, hlen); store8(hex_value + hlen, 0);`, and the not-found arm at :690-693 `hex_value = alloc(default_hex_len + 1); memset(hex_value, 48, default_hex_len);`. `tpm_pcr_value_new(idx, bank, hex_value)` (:494) stores the pointer verbatim; the struct comment reads `# value is a pointer to a hex string`. The OTHER operand IS boxed: svc_config.cyr:378-383 pushes `json_v_str(e)`.

`edge_is_all_zero_hex` (edge_boot.cyr:122-134, verified verbatim) does `str_len(h)` then `str_data(h)` then `load8(d + i)`; `str_len` is `load64(s+8)` and `str_data` is `load64(s)` (~/.cyrius/lib/str.cyr:56,71). On a 64-byte hex-ASCII buffer those read hex characters as a length and as a pointer. `str_eq` does the same to both operands.

RAN, twice, in independent probes built against the real linked tree with `CYRIUS_DCE=1 cyrius build`, feeding exactly what both producers produce: `str_len(got) = 4051048575092012341`, `str_data(got) = 3761687883739705649` (= 0x3434333332323131 LE, far above the x86_64 47-bit canonical user VA ceiling), then `EXIT=139` (SIGSEGV). A second probe called `_eb_compare_pcrs` itself on the FULLY-MATCHING path — real 64-hex digest as the cstr, the identical digest boxed in `_eb_expected_pcrs` — and also got `EXIT=139`. The zero-fill path (0x3030303030303030 = 3.47e18) is equally fatal.

Not dead code: `strings build/kybernet | grep "PCR read back all-zero - UNREADABLE"` matches in the DCE'd production binary on both arches.

### Trigger

`/etc/kybernet/config.json` with `{"boot_mode":"edge","verify_boot":true,"edge":{"tpm_attestation":true,"pcr_bindings":"7","expected_pcrs":["<any valid non-zero 64-hex digest>"]}}` on a board where `/dev/tpmrm0` or `/dev/tpm0` exists and `/usr/bin/tpm2_pcrread` exists. sigil errors on an empty index list, so `have >= 1` and the `i == 0` iteration always takes the `else` arm. The crash is unconditional on the first iteration — it does not require the PCR to mismatch, to be unreadable, or the TPM to misbehave.

### Consequence

SIGSEGV in PID 1 during phase 6c, before the reactor and before any service: "Attempted to kill init!". Unrecoverable, on every boot, on exactly the deployment shape edge boot exists to serve. The documented cmdline escape hatch does not help — edge_boot.cyr:403-413 DOWNGRADES `kybernet.edge=off` to permissive whenever a root_hash is pinned (i.e. exactly a provisioned edge board), and permissive still runs every check, so it reaches :500 and panics again. Note the file's own header and `_eb_compare_pcrs`' comment both assert the comparison "runs at every edge boot ... and reports drift to dmesg" — it has never run anywhere. It is also the only consumer of `edge_is_all_zero_hex`'s runtime arm, which the header calls the defence against sigil's zero-fill; that defence is a crash.

### Fix

Treat `tpm_pcr_value_value()` as a cstr: wrap once at the top of the loop, `var got = str_from(tpm_pcr_value_value(vec_get(values, i)));`, or add cstr-taking siblings (`strlen` / `streq` against `str_data(want)`). Then close the gate hole: this is standing rule 27 literally — `grep -rn "tpm\|pcr" qemu/` returns only `"tpm_attestation": false` in all four fixtures, and src/test.cyr:2158-2163 exercises `edge_is_all_zero_hex` ONLY via `str_from(...)`, never via a `tpm_pcr_value`, with no test of `_eb_compare_pcrs` at all. The roadmap already records that swtpm 0.10.1 + tpm2-tools 5.8 make this harness work rather than hardware work; add the fixture. While in there: `_eb_compare_pcrs` matches baselines POSITIONALLY and never checks `tpm_pcr_value_index(v)`, so `pcr_bindings: "14+7"` with `expected_pcrs: [d7, d14]` silently reports two mismatches.

## HIGH-1 — The health-poll cadence is derived from `config_services()` only, so argonaut's default services are never counted — their watchdog deadlines expire between ticks and PID 1 SIGKILLs healthy services on every default boot

**Severity:** HIGH  **Where the fix lands:** `kybernet`  **Site:** `src/main.cyr:1456`  
**Class:** wrong input set — a derived timer inconsistent with the deadline it exists to satisfy

**Status:** **CLOSED in 1.6.13.** `_health_interval_for_config` now reads `init_service_defs(g_init)` — the live registered set — falling back to the config half only before argonaut is initialised.

> **Re-verified by hand.** Independently confirmed: `lib/argonaut_services.cyr` lines 143-236 show the default services DO carry health checks at 5000/10000/15000 ms, and `_health_interval_for_config` read only `config_services`.

### Evidence

src/main.cyr:1454-1456 `fn _health_interval_for_config() { if (g_config == 0) { return 30; } return health_interval_from_services(config_services(g_config)); }`. `config_services(cfg)` is `load64(cfg + 8)` — the CONFIG half only. `init_poll_health` and `init_check_watchdog` both iterate `load64(init + 16)`, the full service map, which `argonaut_init_new` (lib/argonaut_init.cyr:28-45, read verbatim) populates from `default_services(mode)` FIRST and config services second. src/main.cyr:1604-1607 only re-arms when `hiv != 30`, so with no config health checks the timer stays at its phase-5 value of 30 s.

Measured by probe against the resolved deps: `health_interval_from_services(empty) = 30`; `default_services(BOOT_DESKTOP)` registers 7 services, ALL with health checks — aethersafha `interval 5000 / timeout 1000 / retries 2` => watchdog_ms 11000, redis/daimon/agnoshi => 31000-32000, postgres/llm-gateway/ifran => 47000-48000; `health_interval_from_services(defaults) = 5`. `init_check_watchdog` (lib/argonaut_init.cyr:906-926, read verbatim) computes `watchdog_ms = interval * retries + timeout` and kills when `elapsed > watchdog_ms`, where `elapsed = uptime` while `last_hc == 0`. `last_hc` is written ONLY at spawn and on a health PASS, so it can only be refreshed as often as kybernet's 30 s tick. `argonaut_config_default()` is BOOT_DESKTOP, and `start_services` correctly walks `init_service_defs(g_init)`, so the defaults really are started and really do reach STATE_RUNNING with a live pid in the proc table.

### Trigger

Any board with no `/etc/kybernet/config.json`, or with a config whose own `services` array defines no `health_check`. Timeline: phase 5 arms health@30 s and watchdog@10 s; phase 8 starts aethersafha at T0 (~1 s) with `last_hc = T0`; the watchdog tick at t=20 s computes `elapsed = 20000 - T0 > 11000`.

### Consequence

`init_enforce_watchdog` SIGKILLs the Wayland compositor ~20 s into every boot — before its first health probe has run, while it is completely healthy. `handle_watchdog_tick` queues a restart at +2 s; `init_restart_service` re-seeds `last_hc` and the same kill lands 11-20 s later. `restart_config_default()` caps this at max_restarts 5, so the service is permanently dead within ~2 minutes. redis/daimon/agnoshi (31-32 s deadlines) sit ~2 s inside the ~30 s worst-case gap, so a single transient probe failure (which leaves `last_hc` unwritten) kills them too — while `handle_health_tick` is simultaneously refusing to restart them because `health_tracker_count < retries`. The `retries` tolerance is functionally 1 across the whole default set. Aggravating: the comment at src/lib/svc_config.cyr:633-637 reasons that watchdog sizing is "consistent by construction" because the tick is the minimum configured interval — a conclusion that is false precisely because the minimum is taken over the wrong set, so the wrong belief is documented in-tree. No gate can see it: loop mode takes the `g_loop_harness == 1` branch and never calls `_health_interval_for_config`, and the harness config is `"boot_mode": "recovery"`, for which `default_services` returns an empty vec.

### Fix

Feed the full registry: `return health_interval_from_services(init_service_defs(g_init));` — the accessor argonaut added at 1.10.0 for exactly this bug class (its own header names kybernet's `resolve_service_waves(config_services(config))` as the defect it was written to fix; `start_services` was corrected at 1.5.0 and this call site was not). Note `init_service_defs` alone yields 5 s, which satisfies aethersafha's 11 000 ms deadline by only ~1 s of margin under worst-case `_hc_is_due` alignment — so also refuse or warn at load when the derived tick period cannot satisfy `min(interval * retries + timeout)`, and add a non-loop-mode harness fixture with a non-recovery boot_mode so this path is executed by a gate at all.

## HIGH-2 — Landlock rulesets are frozen at ABI v1, so `truncate(2)` is completely unrestricted for every confined service while the sandbox reports "applied"

**Severity:** HIGH  **Where the fix lands:** `kybernet`  **Site:** `src/lib/sandbox.cyr:107`  
**Class:** incomplete sandbox coverage — a silent capability gap in the LIVE per-service confinement path

**Status:** **DEFERRED** to [roadmap.md](../development/roadmap.md) with the evidence below.

### Evidence

`_landlock_handled_mask()` (src/lib/sandbox.cyr:107-115, read verbatim) ORs exactly the thirteen ABI-v1 access bits EXECUTE(1) .. MAKE_SYM(4096) = 8191 (0x1FFF, bits 0..12). It omits LANDLOCK_ACCESS_FS_TRUNCATE (1<<14, ABI v3 / Linux 6.2) and LANDLOCK_ACCESS_FS_IOCTL_DEV (1<<15, ABI v5). A Landlock ruleset governs only the operations named in `handled_access_fs`; anything absent is not checked at all. `grep -rn "16384|32768|TRUNCATE|IOCTL_DEV|CREATE_RULESET_VERSION" src/` returns nothing — there is no ABI negotiation anywhere.

Measured twice independently, on this host (Linux 7.1.9, Landlock ABI 9 reported by `landlock_create_ruleset(NULL,0,1)`), driving the REAL `svc_apply_security_json` + `sandbox_from_config`, and separately re-derived with a ctypes probe using no repo code. Config `{"security":{"landlock":[{"path":"/usr","access":"read-exec"}]}}`:
  sandbox_from_config -> Ok(0) ("applied")
  open(victim, O_WRONLY)  -> -13 EACCES   <- Landlock IS enforcing
  truncate(victim, 0)     ->   0          <- BYPASS, 16 bytes -> 0 bytes
Control, identical ruleset with `_landlock_handled_mask() | 16384`: create_ruleset=3, add_rule=0, restrict_self=0, then `truncate(victim2,0) -> -13 EACCES`, file unchanged. The omitted bit is the sole cause.

### Trigger

Any service with a `security.landlock` block, on any kernel >= 6.2. The shipped harness fixture `kyb-landlock` (qemu/build-initramfs.sh:419-428) grants /usr read-exec and /dev read-write and runs as ROOT; a process under that policy can still `truncate("/etc/shadow", 0)` or `truncate("/boot/vmlinuz", 0)`.

### Consequence

Landlock-confined services are not confined against file destruction. Because the uid drop is opt-in and (see HIGH-3) mutually exclusive with a capability policy, the overwhelmingly common shape is a ROOT service under Landlock — for which DAC imposes nothing either — so path-based `truncate()` reaches every file on the filesystem. Zeroing /etc, the kernel image or a dm-verity hash device is a bricked or unbootable board, and `kyb_pre_exec` reports the sandbox successfully applied throughout. IOCTL_DEV's absence additionally leaves arbitrary device ioctls unchecked on any /dev node the ruleset lets the service open. This is the same shape as the previous audit's HIGH-3 (seccomp with no arch check): an entire operation class escaping a mechanism that reports success.

### Fix

Negotiate the ABI instead of hardcoding v1. Call `syscall(SYS_LANDLOCK_CREATE_RULESET, 0, 0, 1)` once; on a negative return keep the existing Ok(1) "no Landlock" arm. Otherwise build the mask incrementally: v1 bits always, `| TRUNCATE (1<<14)` when v>=3, `| IOCTL_DEV (1<<15)` when v>=5. Adding the bits unconditionally is NOT a fix and this was tested: an unknown access right makes `landlock_create_ruleset` return -22 EINVAL, so on a 5.13..6.1 kernel `sandbox_apply` would return Err and every confined service would refuse to start. Do NOT add REFER (1<<13) as a "missing" bit — probed and refuted: with REFER unhandled the kernel denies ALL cross-directory rename/link (measured EXDEV), so its absence is fail-CLOSED. Add a harness assertion that a truncate of a non-granted path is denied; qemu/landlock-fixture.cyr only ever calls `sys_open(O_RDONLY)`, which is why this survived (rule 27).

## HIGH-3 — `capabilities` and `uid`/`gid` cannot be used together — the capability drop strips CAP_SETUID/CAP_SETGID before the privilege drop needs them, so the service never starts

**Severity:** HIGH  **Where the fix lands:** `kybernet`  **Site:** `src/lib/service_sandbox.cyr:113`  
**Class:** ordering defect in the privilege-drop sequence (capability surrender precedes the setuid that requires it)

**Status:** **DEFERRED** to [roadmap.md](../development/roadmap.md) with the evidence below.

### Evidence

`kyb_pre_exec`'s order, read verbatim: cgroup(87) -> no_new_privs(108) -> capabilities(113) -> Landlock(131) -> PRIVILEGE DROP(186) -> seccomp(201). `drop_caps_from_set` -> `drop_capabilities` -> `drop_cap_sets(keep_mask)` (privdrop.cyr:104-125) issues capset(v3) with effective = permitted = keep_mask, so anything off the keep-list is gone from the EFFECTIVE set before `drop_privileges` runs. The kernel gates setgroups/setgid on `ns_capable_setid(CAP_SETGID)` and setuid on CAP_SETUID, not on euid==0. svc_config.cyr:515-559 parses `capabilities` and `uid`/`gid` from the SAME `security` object with no cross-validation.

Measured end to end through the PRODUCTION functions under `unshare --map-auto --map-root-user`, with controls:
  A `{"capabilities":["cap_net_bind_service"],"uid":65534,"gid":65534}` -> svc_apply_security_json = 1 (ACCEPTED); kyb_pre_exec = 1 => argonaut `sys_exit(126)`, service never starts; uid still 0.
  B same config minus `capabilities` -> kyb_pre_exec = 0, uid 65534. Works.
  C keep-list = cap_setuid + cap_setgid + cap_net_bind_service -> kyb_pre_exec = 0, uid 65534, and /proc/self/status then reads `CapPrm 0  CapEff 0  CapAmb 0  CapBnd 0x4c0`.
B and C isolate the cause: the only variable is whether CAP_SETUID/CAP_SETGID survive the keep-list. `grep -rn 'PR_SET_KEEPCAPS|KEEPCAPS|CAP_AMBIENT|SECBIT' src/ lib/argonaut_*.cyr lib/agnostik.cyr` returns NOTHING, and drop_cap_sets stores inheritable=0 explicitly.

### Trigger

`"security": {"capabilities": ["cap_net_bind_service"], "uid": 65534, "gid": 65534}` — the canonical "listen on :443 as an unprivileged user" policy. Also fires for `"capabilities": []` (the documented "drop everything" form, keep_mask = 0), which is the hardening an operator is most likely to pair with a uid.

### Consequence

The service refuses to start. For `type: oneshot`/`forking` the parent sees the 126 and logs `FAILED to start: <name>`; for `type: simple` argonaut returns the forked pid, so kybernet logs `started: <name>` and the dead child surfaces later as a SIGCHLD/restart-queue loop with nothing naming the privilege drop — quieter, not milder. If it is the only enabled service, `failed > 0 && started == 0` can drop the board to the emergency shell. In the workaround shape (C) the service does start, as uid N with ZERO capabilities — CapAmb is 0, no_new_privs makes file capabilities inert, so execve computes pP' = 0 and the `capabilities` key is a silent no-op for any non-root service — while forcing the operator to keep CAP_SETUID and CAP_SETGID in the BOUNDING set, the two capabilities you least want a service able to regain. The intersection of the two most important security keys is unusable, and the failure is discovered on the board rather than at config load.

### Fix

Reorder, or make the capability step preserve what the drop needs: (1) `prctl(PR_SET_KEEPCAPS, 1)`; (2) drop the bounding set to keep_mask; (3) setgroups/setgid/setuid; (4) `capset(effective = permitted = inheritable = keep_mask)`; (5) `PR_CAP_AMBIENT_RAISE` each cap in keep_mask so it survives execve; (6) `prctl(PR_SET_KEEPCAPS, 0)`. Steps 5-6 are what actually delivers a capability to a non-root service. Add a harness fixture combining both keys and asserting CapEff/CapPrm and Uid from inside the child — rule 27 in person: kyb-confined has `capabilities` and no uid, kyb-nonroot has uid and no capabilities, and no fixture has ever combined them. CHANGELOG's justification of this ordering reasons only about the seccomp allowlist and never considers the step immediately before the drop.

## HIGH-4 — `cgroup_has_pid` allocates 8,200 bytes of never-freed arena per `MAINPID=` datagram — a service-triggerable OOM primitive against PID 1, and a 16x regression of the leak 1.6.3 shipped a fix for

**Severity:** HIGH  **Where the fix lands:** `kybernet`  **Site:** `src/lib/cgroup.cyr:519`  
**Class:** unbounded per-event allocation in the one arena PID 1 never resets (standing rule 8's family)

**Status:** **CLOSED in 1.6.13.** The `cgroup.procs` scratch is a static `_CG_PROCS_BUF[1025]` (1025 slots = 8200 bytes at global scope; see LOW-7) instead of an `alloc()` per datagram. Measured: `.bss` grew 132,848 -> 141,056 bytes, and the per-datagram growth is now zero.

> **Re-verified by hand.** Independently confirmed by reading `cgroup_has_pid`: `var buf = alloc(cap + 1)` with `cap = 8192`, never freed, and `cgroup_file` is cached so it is the only allocation.

### Evidence

src/lib/cgroup.cyr:518-519 `var cap = 8192; var buf = alloc(cap + 1);` — a fresh allocation per call with no free on any of the function's five return paths. Its ONE non-definition call site tree-wide is src/main.cyr:1421 `} elif (cgroup_has_pid(name, claimed) == 0) {`, inside `handle_notify_msg`'s drain loop.

The invariant broken is this repo's own. src/main.cyr:1236 states "The per-datagram path now allocates NOTHING: the receive buffer, the status buffer and the scan slot are all static", written at 1.6.3 to close a 512-byte-per-datagram leak that src/lib/notify.cyr:134-142 calls "A LIVE DENIAL OF SERVICE", and a 152-byte replacement that main.cyr:1226-1232 rejects with "A reduction is not a fix." 1.6.10's MAINPID feature reintroduced the same class on the same path at 16x, and neither the comment nor CHANGELOG noticed.

### Trigger

Any process that is uid 0 AND the live pid of a service in kybernet's table — i.e. any of the board's own services, or anything that has compromised one; exactly the threat model src/lib/notify.cyr:85-93 states the SO_PASSCRED work exists to address. It writes `MAINPID=<digits>` to $NOTIFY_SOCKET in a loop. `NOTIFY_DRAIN_MAX = 32` bounds only the per-wakeup drain; the socket is level-triggered so the reactor re-fires immediately while data is queued. Already exercised once per harness boot by qemu/notify-fixture.cyr:106.

### Consequence

Monotonic, unreclaimable growth in the arena PID 1 never resets. VA grows 8,200 B/datagram; RSS grows ~1 page per datagram (`file_read_all` does not memset, and the 8,200-byte stride puts each small write on its own page), so ~4 KiB/datagram of real RAM. PID 1 is OOM-exempt, so the kernel kills every other process first and then panics with "Out of memory and no killable processes" — the same terminal state notify.cyr:134-142 documents for the 512-byte version it replaced, reached 16x faster. This call site does guard `if (buf == 0)` and fails closed, so the fault does not occur here; by then every other, unguarded allocation in PID 1 is failing.

### Fix

Move the buffer to BSS, matching the precedent notify.cyr:160-161 established for exactly this reason: `var _cg_procs_buf[8193];   # 8193 BYTES == 8192 cap + 1 headroom (rule 2)` at file scope, then `var buf = &_cg_procs_buf;`. The `if (buf == 0)` guard goes away with the failure mode it handled, and the `n > cap` truncation refusal and whole-line pid compare are untouched, so the security property is preserved. PID 1 is single-threaded with one non-reentrant caller, so a shared buffer is sound — state that at the declaration. Then GATE the class, because reading missed it twice: emit `alloc_used()` in the shutdown summary beside the existing notify tallies, have qemu/notify-fixture.cyr send N MAINPID claims, and assert in the `harness=loop` pass that arena usage does not scale with N. Nothing in src/test.cyr, src/bench.cyr or qemu/ currently measures per-call allocation anywhere.

## HIGH-5 — Every SIGHUP leaks 53,640 bytes of arena, 65% of it a read buffer and a service-definition set that `reload_config` explicitly refuses to apply

**Severity:** HIGH  **Where the fix lands:** `kybernet`  **Site:** `src/main.cyr:149`  
**Class:** unbounded per-signal allocation; work performed only to be discarded

**Status:** **DEFERRED** to [roadmap.md](../development/roadmap.md) with the evidence below.

### Evidence

src/main.cyr:148-150 `var cap = 16384; var buf = alloc(cap + 1); var n = file_read_all("/etc/kybernet/config.json", buf, cap + 1);` and :268-273, which builds every ServiceDefinition on every call, while src/main.cyr:360-362 then throws that set away: `if (vec_len(config_services(new_cfg)) > 0) { klog("config reload: service definitions require a reboot - NOT applied"); }`.

Measured by two independent probes replicating `load_config` verbatim against the repo's own qemu/initramfs/etc/kybernet/config.json (4,678 bytes, 13 services), `alloc_used()` delta over 100 iterations after warm-up: **53,640 bytes per reload**, decomposed as read buffer 16,392 + json value tree 18,520 + argonaut_config_default 464 + svc_defs_from_json 18,264. ### Trigger

`kill -HUP 1` from any root process. SIGHUP is not queued, so the rate is one reload per reactor iteration; a shell loop drives thousands per second. No attacker is required either: a config-management agent that HUPs PID 1 once a minute costs ~77 MB/day in a process CLAUDE.md says runs for months.

### Consequence

Root-triggerable memory exhaustion of PID 1, and slow unbounded growth under entirely legitimate use. 5,003 reloads per 256 MiB chunk; every allocated byte is written (JSON tree + service defs), so this is real RSS, not just VA. PID 1 is OOM-exempt, so the terminal state is the same kernel panic as HIGH-4. Even a REFUSED reload (absent, truncated or malformed config) still leaks ~16.4 kB per HUP while correctly keeping the running config.

### Fix

Two independent halves. (a) Make the read buffer static: `var _cfg_read_buf[16385];` in BSS — it is a fixed 16 KiB by construction and the `n > cap` truncation refusal is unaffected. This was checked for aliasing and is safe: `_jp_parse_string_a` pre-scans for the closing quote and copies each decoded string into its own allocation before `str_new_a`, so no tree node points into the read buffer. (b) Give `reload_config` a narrow load path that parses only the keys it is documented to apply (boot_timeout_ms, shutdown_timeout_ms, log_to_console, emergency_require_auth, emergency_password_hash) and never calls `svc_defs_from_json` — the function's own header already says structural changes need a reboot, so building 13 ServiceDefinitions to log "NOT applied" is pure waste. That removes 34,656 of the 53,640 bytes. Also check `alloc()`'s return before handing the pointer to `file_read_all`. The residual JSON tree is inherent to re-parsing and should be bounded by rate-limiting reloads rather than by allocation tricks.

## MEDIUM-3 — `health_check` fields are parsed with zero validation while `interval_ms * retries + timeout_ms` drives a SIGKILL — `"retries": 0` gives a 2 s watchdog deadline and `"retries": -1` a negative one that fires unconditionally

## MEDIUM-4 — `"health_check": {"type": "http"}` uses a BLOCKING `connect(2)` with no timeout, stalling PID 1's reactor for the kernel's full SYN-retry window

**Severity:** MEDIUM  **Where the fix lands:** `argonaut`  **Site:** `lib/argonaut_health.cyr:335`

**Status:** **DEFERRED** to [roadmap.md](../development/roadmap.md) with the evidence below.

### Evidence

lib/argonaut_health.cyr:326-340, the HC_HTTP_GET arm: `var fd = sys_socket(2, 1, 0); ... var ret = sys_connect(fd, &addr, 16); if (ret == 0) {`. There is NO `ag_sys_fcntl(fd, 4, 2048)` (F_SETFL, O_NONBLOCK) between the socket and the connect, no `-115` EINPROGRESS arm, and no poll around it; a non-zero return goes straight to `message = str_from("HTTP connect failed")`. `sys_connect` is a bare `syscall(SYS_CONNECT, ...)`. The contrast is in the same file, ~230 lines above: `tcp_connect_ip` (:71-95) does `ag_sys_fcntl(fd, 4, 2048)` before `sys_connect`, handles `ret == -115`, and bounds the wait with `ag_sys_poll(&pollfd, 1, timeout_ms)` plus the SO_ERROR check carrying its own 1.5.5 fix. So the TCP arm is bounded and the HTTP arm is not.

Config reachability: src/lib/svc_config.cyr:93 -> lib/argonaut_types.cyr:223 `if (str_eq_cstr(s, "http") == 1) { return Ok(HC_HTTP_GET); }`. Every guard before the connect was checked and none blocks a dotted-quad target: `http://` scheme, port 1..65535, host sanitizer, and `resolve_host_ipv4` (which is parse_ipv4 + /etc/hosts, no DNS). Measured: `/proc/sys/net/ipv4/tcp_syn_retries` = 6 here, and the kernel's exponential backoff sums 1+2+4+8+16+32+64 = 127 s. Rule 27: the only fixtured health-check type is `tcp`; `grep -rn http qemu/` returns nothing.

### Trigger

`"health_check": {"type": "http", "target": "http://10.0.0.5:8080/healthz", "timeout_ms": 200}` where 10.0.0.5 silently drops SYN — host down, firewall DROP rather than REJECT, cable pulled. Ordinary for a service whose health endpoint lives on another box.

### Consequence

During each stall PID 1 reaps no zombies, handles no SIGTERM/SIGCHLD, services no watchdog and drains no notify socket; with a poll interval shorter than the stall the board is unresponsive essentially continuously and a shutdown request sits unhandled for minutes. Less severe than MEDIUM-4's sibling HIGH-6 only because the kernel eventually returns. Scope note: `execute_ready_check` funnels into the same function, but kybernet's parser never builds a ready_check, so the boot path is not additionally exposed.

### Fix

In the HC_HTTP_GET arm, do what `tcp_connect_ip` already does: `ag_sys_fcntl(fd, 4, 2048)` before `sys_connect`, treat -115 as EINPROGRESS, bound it with `ag_sys_poll(&pollfd, 1, timeout)` plus the SO_ERROR check. Better, factor the bounded connect out of `tcp_connect_ip` and call it from both arms so the two cannot drift again. Then fixture `"type": "http"` against a blackholed address and assert in the `harness=loop` pass that the reactor keeps ticking.

## MEDIUM-9 — aarch64: `sys_pause()` issues `flock(0,0)` and returns immediately, turning every deliberate PID-1 halt into a 100% CPU busy-spin and disarming four failure backstops

**Severity:** MEDIUM  **Where the fix lands:** `cyrius`  **Site:** `src/main.cyr:497`  
**Class:** arch-dependent syscall number hijacked by the ESYSXLAT ladder; a blocking primitive that does not block

**Status:** **DEFERRED** to [roadmap.md](../development/roadmap.md) with the evidence below.

### Evidence

lib/syscalls_aarch64_linux.cyr:111 `SYS_PPOLL = 73;  # -> sys_pause (NULL fds, NULL timeout)` and :688-690 `fn sys_pause(): i64 { return syscall(SYS_PPOLL, 0,0,0,0,0); }`. 73 is aarch64-native ppoll, but the ladder reads 73 as x86_64 `flock` and rewrites it to aarch64 32.

Proven by execution and by disassembly of the emitted ELF, not by reading. `qemu-aarch64 -strace` on a probe: `write(1,...)before` / `flock(0,0,0,0,0,0) = -1 errno=22 (Invalid argument)` / `write(1,...)after`. `llvm-objdump -d` on the aarch64 binary shows the ladder emitted inline: `cmp x8, #0x49 (73) / b.ne / mov x8, #0x20 (32)`, and that arm precedes the `cmp x8, #0x7` poll->ppoll fixup, so a direct source-73 never reaches ppoll. The IDENTICAL source built for x86_64 blocks (`timeout 3` exits 124). A spin probe completed 1,000,000 `sys_pause()` calls in 0.50 s wall at 99% CPU under emulation.

Six call sites in src/main.cyr: :467 and :497 are `while (1 == 1) { sys_pause(); }` in `drop_to_emergency`, both directly under kmsg lines reading "halting rather than reboot-looping" / "Halt, do NOT reboot"; :665 guards do_shutdown after `sys_reboot`; :1523/:1545 are followed by `return 1` out of `kybernet_run`; :1663 is the phase-6c edge refusal whose `if` block ends immediately after it.

⚠ SCOPE, checked rather than assumed: `SYS_REBOOT = 142` is NOT hijacked — probed under strace, it dispatches as a real `reboot(0xfee1dead, 0x28121969, ...)`. kybernet never drops PID 1's own capabilities (`grep` confirms every privdrop entry point has exactly one caller, inside `kyb_pre_exec`, i.e. the forked child), so `sys_reboot` succeeds and does not return. The four post-shutdown sites are therefore a DEFEATED BACKSTOP, not a live path.

### Trigger

Any aarch64 board reaching `drop_to_emergency` with `emergency_require_auth` set and either a failed authentication or an unopenable /dev/console. Currently masked by CRITICAL-1 (the boot dies at phase 4); it becomes live the moment signalfd is fixed. x86_64 is unaffected.

### Consequence

What the code and its own comments call a halt is on aarch64 an unkillable tight loop issuing `flock(0,0)` at syscall rate, pinning a core forever — on exactly the fanless, battery-constrained edge hardware AGNOS targets, with signals blocked and no way back, and with no diagnostic distinguishing it from the intended halt. Separately, the four post-`sys_reboot` guards stop guarding: if `sys_reboot` ever did return, :1523 falls through to `return 1` -> `sys_exit(1)` = "Attempted to kill init" (standing rule 4's exact hazard, silently disarmed on this arch), and :1663 falls straight through into phases 7/8/9 and boots every service on an edge board whose verification was just refused (the 1.4.2 HIGH-2 outcome). ## LOW-7 — Standing rule 2 states a fact measurement contradicts — `var X[N]` is N BYTES for a LOCAL and N SLOTS (N*8 bytes) for a GLOBAL — and the prior audit's `HANDLED_SIGNALS` refutation gives the wrong reason

**Status:** **CLOSED in 1.6.13.** Standing rule 2 rewritten to state both halves, with the measurement.

NO CODE DEFECT — I enumerated all 24 `var X[N]` declarations in src/main.cyr and src/lib/. ### Trigger

No current code trigger. Amend the 2026-08-24 refuted-list entry to give the real reason: HANDLED_SIGNALS is a file-scope `[1]` = 8 bytes holding the 8-byte pointer `sigset_new()` returns.
